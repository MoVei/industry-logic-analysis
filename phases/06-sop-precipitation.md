# Phase 6: SOP 沉淀与定级

| | |
|---|---|
| **输入** | 通过审校的五件套 |
| **输出** | `references/domain-playbooks/<大类>-<细分>.md` + 台账追加 + 复用脚本状态更新 |
| **前置条件** | Phase 5 完成，审校通过 |
| **完成条件** | SOP 九要素齐全、已定级、已写失效条款、台账已追加 |

---

## 前置原则：每份 SOP 必须独立取证

```
每份 SOP 的数据与机制，必须来自本次执行的 Phase 1—4 实地检索结果
```

**明确禁止**：

- ❌ 从既有产出、历史文章、笔记中**转录**数据作为 SOP 内容
- ❌ 用「上一期顺手整理」「之前分析过」代替本期的检索动作
- ❌ 把其他文档的结论当作本 SOP 已验证的依据

**允许**：把既有产出当作「去哪找线索」的**检索起点**，找到后仍须回到 L0—L2 原始发布方核对取数。

> 这条规则的实质：SOP 的权威性建立在「本轮现场取证」上。二手转录会继承来源当时的口径与错误，且无法验证。

---

## 步骤 6.1：按九要素填写 SOP

模板见 `references/domain-playbooks/_template.md`。**缺任一要素即判定不合格**：

1. **那根杠杆**：传导方向 + 量化时长 + 敏感性区间
2. **完整对冲变量清单**：每个变量的影响量级
3. **数据清单**：每项绑定**具体数据源 + 具体报表名 + 口径 + 更新频率 + 访问方式**。写「参考行业数据」不合格
4. **历史实证区间**：≥1 个完整案例含数字
5. **常见误读与纠错**：❌/✅ 成对列出
6. **口径陷阱表**：哪些数字不能互相比较
7. **跟踪信号表**：指标 / 发布方 / 频率 / 阈值 / 信号桶
8. **失效条款**（见 6.3）
9. **定级 + last_verified + verification_log**

## 步骤 6.2：定级

| 级别 | 门槛 | 使用时的标注要求 |
|---|---|---|
| **Draft 草案** | 完成首期分析 + ≥1 个历史实证区间 + 数据清单完整 | 必须标注「未经滚动验证」 |
| **Verified 已验证** | 被复用 ≥2 期（或跨越 ≥2 个不同时点），且至少 1 次机制方向判断被事后数据证实 | 标注 last_verified 日期 |
| **Authoritative 权威** | 复用 ≥3 期 + 跨越一个完整周期/阶段 + 无未决反例 | 可直接作为该行业的基线认知 |

**初次沉淀一律 Draft。** 不允许因为「写得很完整」而跳级。

## 步骤 6.3：写失效条款 ★

每份 SOP 必须赋予自己一个「到期日」。至少三条，其中前两条是强制的：

```
失效条款 F1（强制）
若 <具体数据源> 停止更新或变更口径
→ 本 SOP 自动降级为 Draft，30 日内寻找替代源

失效条款 F2（强制）
若连续 2 期机制判断被数据证伪
→ 主链条作废，回到 Phase 3 重新考古

失效条款 F3（按行业特性自定）
若行业结构发生 <X 条件>
→ 本节暂停适用
   例：生猪规模化率超过某阈值后，散户行为模型失效
   例：某产品进口依存度降到某比例以下后，海外定价逻辑不再主导
```

## 步骤 6.4：追加台账

写入 `references/ledger-analysis-topics.md`，字段：

```
大类 / 细分标的 / 期号 / 生活入口 / 切入角度（那根杠杆）/ 核心案例 / 关键数据（含期间）/ SOP 是否已沉淀 / SOP 定级 / 验证结论
```

**动笔前必读、写完后必追加。** 台账是防重复的唯一防线。

## 步骤 6.5：登记定级状态

更新 `references/domain-playbooks/README.md` 的索引表：文件名 / 行业 / 定级 / last_verified / 当前状态。

## 复用已沉淀 SOP 时的强制检查

执行 `python scripts/helpers/check-sop-freshness.py --all` 或直接按下列两条手查：

### ① 时效检查

| 数据类型 | 超过天数必须重新取数 |
|---|---|
| 月度数据 | >45 天 |
| 季度数据 | >105 天 |
| 年度数据 | >400 天 |

超期 → **必须重新取数**，不许沿用旧读数。

### ② 反例检查

查阅该 SOP 的 `verification_log`，确认无未决反例。有未决反例 → 在产出中明示该 SOP 当前不可靠，并降为 Draft。

### ③ 每次使用后必做

在 `verification_log` 追加一行：

```
| 使用日期 | 当期读数 | 机制方向是否符合预期 | 是否发现新反例 | 期号 |
```

## 反馈规则

```
IF SOP 九要素有缺项
    THEN 不得沉淀
    AND  回到对应 Phase 补齐（缺历史实证 → 回 Phase 3.4）

IF 后续使用中出现第 2 个未决反例
    THEN 立即执行失效条款 F2：主链条作废，重走 Phase 3
```
